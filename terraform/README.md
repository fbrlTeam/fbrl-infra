# terraform (계획 문서)

> **Azure 계정이 생기기 전까지는 계획 문서일 뿐, 실행 코드(`.tf`)는 다음 단계에서 작성합니다.**

## 왜 Terraform인가

- 리소스 그룹, VM, 네트워크/보안그룹 등 Azure 리소스를 코드로 남겨 재현 가능하게 만들기 위해.
- 콘솔 클릭으로 만든 리소스는 나중에 무엇을 왜 그렇게 설정했는지 추적이 안 됨 — 코드는 그 자체가 기록.
- dev 환경을 날리고 다시 만드는 일이 생겨도(예산 문제로 껐다 켜기 등) 동일한 구성을 빠르게 재현할 수 있음.

## 만들어야 할 Azure 리소스 (우선순위 순)

1. **리소스 그룹** — 이 프로젝트의 모든 리소스를 묶는 컨테이너. 가장 먼저 필요.
2. **VM (k3s용)** — 예산 제약으로 AKS 대신 VM 위에 k3s를 직접 설치하는 방향. 저비용 스펙 후보:
   - `B2s` (2 vCPU, 4GB RAM) — 가장 저렴하지만 postgres+redis+kafka+kafka-connect+jaeger를 한 노드에 다 올리면 메모리가 빠듯할 가능성 있음
   - `B2ms` (2 vCPU, 8GB RAM) — 여유 있는 절충안, 현재 가장 유력한 후보
   - `B4ms` (4 vCPU, 16GB RAM) — Kafka Connect + 트레이싱까지 안정적으로 돌리고 싶으면 고려, 대신 비용 제일 높음
   - Azure 계정 개설 후 실제 가격표 기준으로 재비교 필요.
3. **네트워크/보안그룹** — 열어야 할 포트:
   - `22` (SSH, 관리용)
   - `6443` (k3s API 서버)
   - 백엔드 애플리케이션 포트(Spring Boot 기본 `8080`, 확정 필요)
   - 그 외 postgres(`5432`)/redis(`6379`)/kafka(`9092`)는 원칙적으로 클러스터 내부 통신만 하고 외부에 열지 않는 방향으로 검토
   - `22`, `6443`은 관리자 IP만 허용, 그 외는 차단
4. **(선택) 관리형 PostgreSQL vs VM 내부 설치**
   - **Azure Database for PostgreSQL (관리형)**: 백업/패치가 자동화되고 `wal_level=logical` 같은 파라미터도 파라미터 그룹으로 관리 가능. 대신 비용이 VM 자체 설치보다 높고, 예산 제약 기조와는 어긋남.
   - **VM 안에 직접 설치**: 비용은 가장 낮지만(이미 떠 있는 VM 리소스 재사용), 백업/패치/장애 복구를 직접 챙겨야 하고 `wal_level=logical` 등 설정을 수동으로 관리해야 함. 현재 예산 제약 상황에서는 이쪽이 우선 후보.
   - 최종 결정은 Azure 계정 개설 후 실제 관리형 서비스 가격을 확인하고 내림.

## 폴더 구조 제안

지금 규모(단일 dev 환경, 리소스 4종 미만)에서는 `modules/` + `environments/dev` 로 나누는 건
과설계로 보입니다. 당장은 `terraform/main.tf` 하나(또는 `main.tf`/`variables.tf`/`outputs.tf`
정도로만 분리)로 시작하고, staging/prod 환경이 실제로 생기는 시점에 `environments/`로
쪼개는 게 낫다고 생각합니다. 지금 모듈화를 미리 해두면 아직 존재하지 않는 환경 차이를
가정하고 추상화를 만드는 셈이라 오히려 유지보수 부담만 늘어남.

## State 파일 관리

팀 프로젝트이므로 로컬 state는 피하는 게 맞습니다. 로컬 state는 파일이 하나뿐이라
공유가 안 되고(누가 최신 상태를 갖고 있는지 알 수 없음), 실수로 git에 커밋되면 리소스
정보(때로는 민감정보)가 그대로 노출됩니다. **Azure Storage Account에 원격 저장(`azurerm`
backend)**을 쓰는 편이 나음 — state locking도 지원되어 동시 apply로 인한 충돌도 막을 수
있습니다. 다만 이 Storage Account 자체는 Terraform으로 관리하지 않고(순환 의존성 방지)
Azure 계정 개설 직후 수동으로 한 번 만들어두는 방식이 일반적입니다.

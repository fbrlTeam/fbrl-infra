# terraform (계획 문서)

> **Azure 계정이 생기기 전까지는 계획 문서일 뿐, 실행 코드(`.tf`)는 다음 단계에서 작성합니다.**

## 왜 Terraform인가

- 리소스 그룹, VM, 네트워크/보안그룹 같은 Azure 리소스를 코드로 남겨두면 나중에 그대로
  재현할 수 있다.
- 콘솔에서 클릭해 만든 리소스는 왜 그렇게 설정했는지가 시간이 지나면 사라진다. 코드는 그
  자체로 기록이 된다.
- 예산 때문에 dev 환경을 껐다 켜는 일이 생겨도, 같은 구성을 빠르게 다시 만들 수 있다.

## 만들어야 할 Azure 리소스 (우선순위 순)

1. **리소스 그룹** — 이 프로젝트의 리소스를 전부 묶는 컨테이너다. 가장 먼저 만들어야 한다.
2. **VM (k3s용)** — 예산 문제로 AKS 대신 VM에 k3s를 직접 얹는 방향으로 가고 있다. 저비용
   스펙 후보는 이 정도다:
   - `B2s` (2 vCPU, 4GB RAM) — 가장 저렴하지만, postgres·redis·kafka·kafka-connect·jaeger를
     한 노드에 다 올리면 메모리가 부족할 수 있다.
   - `B2ms` (2 vCPU, 8GB RAM) — 여유를 둔 절충안이고, 지금으로선 가장 유력하다.
   - `B4ms` (4 vCPU, 16GB RAM) — Kafka Connect와 트레이싱까지 안정적으로 돌리려면 고려할
     만하지만, 비용이 제일 높다.
   - 최종 스펙은 Azure 계정을 만든 뒤 실제 가격표를 보고 다시 비교해야 한다.
3. **네트워크/보안그룹** — 열어야 할 포트는 다음과 같다:
   - `22` (SSH, 관리용)
   - `6443` (k3s API 서버)
   - 백엔드 애플리케이션 포트(Spring Boot 기본값은 `8080`이지만 아직 확정은 아니다)
   - postgres(`5432`), redis(`6379`), kafka(`9092`)는 클러스터 내부 통신에만 쓰고 외부로는
     열지 않는 쪽으로 검토 중이다.
   - `22`와 `6443`은 관리자 IP만 허용하고 나머지는 전부 차단한다.
4. **(선택) 관리형 PostgreSQL vs VM 내부 설치**
   - **Azure Database for PostgreSQL (관리형)**: 백업과 패치가 자동으로 돌아가고,
     `wal_level=logical` 같은 파라미터도 파라미터 그룹으로 관리할 수 있다. 다만 비용이 VM에
     직접 설치하는 것보다 높아서, 지금의 예산 기조와는 잘 안 맞는다.
   - **VM 안에 직접 설치**: 이미 떠 있는 VM을 그대로 쓰는 만큼 비용은 가장 낮다. 대신 백업,
     패치, 장애 복구를 전부 직접 챙겨야 하고 `wal_level=logical` 같은 설정도 손으로 맞춰야
     한다. 지금 예산 상황에서는 이쪽이 먼저 검토할 후보다.
   - 최종 결정은 Azure 계정을 만들고 관리형 서비스 가격을 실제로 확인한 뒤에 내린다.

## 폴더 구조 제안

지금 규모(단일 dev 환경, 리소스 4종 미만)에 `modules/`와 `environments/dev`까지 나누는 건
과하다. 당장은 `terraform/main.tf` 하나로 시작하거나, 필요하면 `main.tf`, `variables.tf`,
`outputs.tf` 정도로만 쪼개는 편이 낫다. staging이나 prod 환경이 실제로 생기면 그때
`environments/`로 나누면 된다. 아직 존재하지도 않는 환경 차이를 미리 가정하고 추상화부터
만들어두면, 그 구조를 유지하는 부담만 먼저 떠안는 셈이다.

## State 파일 관리

팀 프로젝트인 만큼 로컬 state는 피해야 한다. 파일이 로컬 한 곳에만 있으면 누가 최신 상태를
갖고 있는지조차 알기 어렵고, 실수로 git에 커밋되기라도 하면 리소스 정보—때로는 민감한
값까지—가 그대로 드러난다. **Azure Storage Account에 원격 저장(`azurerm` backend)**하는
쪽이 훨씬 안전하다. state locking도 지원돼서 동시에 apply가 걸리는 충돌도 막아준다. 다만
이 Storage Account 자체는 Terraform으로 관리하지 않는다. 순환 의존성이 생기기 때문에,
Azure 계정을 만들고 나서 수동으로 한 번 만들어두는 게 보통이다.
